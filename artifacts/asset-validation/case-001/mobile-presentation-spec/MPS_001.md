# MPS-001 — Mobile Presentation Specification

Version 1.0 · 2026-10-10 · Case 001 — The Missing Passport.

**Status: definitive documentation proposal for owner review; not approved for implementation or production adoption.** “Must” below expresses the recommended contract if accepted. Existing canonical/frozen requirements remain authoritative now. Owner choices are enumerated in [OWNER_DECISIONS.md](OWNER_DECISIONS.md); an unselected option is never an implemented default. No engineering task is completed by this document.

## 1. Authority and boundaries

Preserve exactly `change-passport-removed`, `change-stands-exchanged` and `change-wallet-moved`. Mara's temporary absence is between snapshots; her stable endpoint presence remains. Wallet stays closed at both endpoints. Do not add clue highlights, changed-only visual treatment, moving people, new props or altered story logic.

Canonical case.json governs normalized visuals and interaction regions. Offline Proposal B and current character composites are testing evidence only; B geometry and candidate assets require independent adoption decisions O05/O07. Presentation recommendations do not select B. Use canonical geometry for any future baseline until separately approved content replaces it.

React/application owns layout, controls, authoritative phases and orchestration. Phaser owns rendering, transient camera/input and semantic selection intents. Domain owns session transitions, selection truth, evidence/scoring. Keep display data free of solutions. Current `phaser-runtime.ts`/`phaser-host.tsx` implement a neutral 960×540 FIT shell with one target; they do not implement this contract. The current bridge only permits its single projected target. Multiobject display/input needs a separately authorized typed bridge extension, not an unsafe cast or raw CaseDefinition handed to Phaser.

## 2. Responsive contract

Reference logical scene: **960×540**, matching frozen Case 001 concept. Support portrait and landscape without mandatory rotation. Proposed QA widths: **320, 390, 430, 768 and 960 effective CSS px**, plus intervening responsive widths; 320/390/960 are primary study points. These are effective scene widths, not hardware screen resolutions. Versions/devices and coverage acceptance remain O08. Widths below 320 after safe areas/text scaling/chrome are a degraded-layout case requiring measurement, not a promise of readable clues.

Allocate a dedicated scene viewport rectangle V=(left,top,A,B) after measuring safe-area and UI space. Fit scale `s=min(A/960,B/540)`; displayed width=960s and height=540s. Center using offsets `ox=(A-960s)/2`, `oy=(B-540s)/2`. Letterbox unused space with a neutral stable color. Never stretch, use cover, crop the initial panorama, rearrange tables by breakpoint or place UI in scene letterboxing if it can obscure/steal scene gestures. A taller host at unchanged width does not enlarge art.

Maximize usable width within the safe area; avoid decorative side padding that reduces 320px to 288px. Height-constrained landscape may produce effective width below nominal device width. Measure actual fit width and treat legibility/target checks accordingly. If no usable complete scene/control layout fits before Start, show a neutral preparation message and await a usable layout; do not start a hidden timer or force an orientation. During active observation, resizing does not create preparation time (see fairness contract).

## 3. Safe area and viewport

Recommended viewport declaration is device-width/initial-scale=1; do not disable user scaling. If edge-to-edge presentation adopts viewport-fit=cover, safe-area environment insets must protect all required content. Apply insets exactly once at the layout boundary; do not subtract them again from already inset measured bounds. [WebKit safe-area guidance](https://webkit.org/blog/7929/designing-websites-for-iphone-x/) explains this dependency.

Prefer dynamic viewport sizing with a tested fallback; neither a fixed 100vh assumption nor installed-PWA status guarantees visible height. Recompute from the scene host's actual content bounds when browser chrome, visual viewport, safe area, orientation or text size changes. Visual viewport resize/scroll can differ from layout viewport changes; retain an explicit consistent pointer coordinate convention rather than double-applying offsets. [VisualViewport documentation](https://developer.mozilla.org/en-US/docs/Web/API/VisualViewport).

Test browser-tab and installed standalone display modes separately. Do not assume fullscreen, orientation lock, stable safe-area values or service-worker/offline support exists. MPS-001 does not authorize PWA installation/caching infrastructure. If future caching is approved, pair assets must come from one accepted revision; stale mixed snapshots are an error, not a visual alternative. Soft keyboard must not shrink an active observation behind a text field: no required text entry during observation. In later text-entry UI, hide/disable scene input while occluded as appropriate to the authoritative phase.

## 4. Scene versus UI

Timer/status above and navigation/evidence/zoom controls below or beside the scene, outside V. Timer is visible in future production observation per GAME_SPEC §7.3; the previous human-test viewer intentionally hid its countdown and is not the production UI contract. Do not use timed audio/text reading as a clue. Reflow UI, not scene objects. Evidence overlays never allow selection through them; showing them cannot freeze an original image. Original scene must not remain behind translucent transition/error/modal UI.

Text scaling keeps UI readable and controls reachable without clipping. Header/footer may scroll outside active observation where safe; never page-scroll the original out of view and then restart its duration. No application debug phase/revision labels or filenames in participant-facing scene UI.

## 5. Phase behavior

| Authoritative phase | Recommended visible/input behavior |
|---|---|
| Briefing / observation_intro | Untimed neutral instructions, load/decode/validate both snapshots and agreed assets; prepare stable layout and explicit Start |
| observation_active | Complete original at 1×; normal **25-second** deadline; no object selection, evidence collection, markers or app zoom by default (O02) |
| observation_end / transition | Hide original immediately; neutral opaque blank for **2 seconds**; clear gestures/focus lens/original previews and reset camera while hidden |
| investigation_intro | Neutral instructions without original; changed scene may appear only after the complete blank; no selection until investigation_active |
| investigation_active | Changed scene initially full 1×; exact canonical targets; optional user zoom/pan only if O01 accepted; approved domain selection/evidence flow |
| Later phases | Existing authoritative flow; no remembered original image through review/back navigation |

This table does not introduce new phases or auto-advance prerequisites. Existing state-machine gates still apply. Sixty seconds was a human free-recall limit, not an investigation gameplay limit; do not import it into the game.

## 6. Investigation camera proposal (O01/O10)

Recommended optional range **1×–2×** using explicit 1×/2× controls; optional pinch can interpolate continuously within those bounds if approved. Full overview is the initial view and always recoverable through a 48px external button. Zoom is neutral, not tied to changed objects. Use viewport-center anchoring for buttons and gesture-centroid anchoring for approved pinch; pan clamps keep no blank space beyond source edges. Do not auto-focus a passport, wallet, stand or discovered object. A floating magnifier is deferred because of mobile occlusion and extra representation complexity.

Camera state is ephemeral presentation state, not canonical/session truth. Retain it while investigating within one stable layout. Before new attempt/phase entry reset to full overview. On ordinary investigation resize, preserve the source point at viewport center if possible, recalculate fit scale and clamp; explicit Overview restores 1×. Observation orientation changes always retain full fit. Cancel every pending selection during camera/layout/phase changes. These reset rules are recommended owner choice O10, not completed behavior.

## 7. Interaction and accessibility

Use [INTERACTION_CONTRACT.md](INTERACTION_CONTRACT.md) for transformations and deterministic target arbitration. Select on confirmed pointer-up, not pointerdown. No tap after pan/pinch/cancel. Provide neutral keyboard spatial selection, external zoom/pan buttons and visible focus, without listing only the three correct changes. Selection on either stand maps to the same canonical exchange through domain logic. Collecting evidence remains a distinct approved action.

Proposed comfort goals: 48×48 CSS-pixel controls/targets, 8px separation; these are design goals pending O03/O08, not replacements for canonical data or WCAG thresholds. Default canonical targets meet these goals at full 320 fit analytically; art correspondence and real taps remain unverified. Do not silently pad/relocate targets when layout shrinks.

Require semantic external controls, keyboard access, single-pointer alternatives to multipoint/drag gestures, visible unobscured focus, readable UI contrast, non-color-only clue design and audio-off usability. Normal UI text target 4.5:1, large text/essential UI boundaries 3:1 where applicable; evaluate actual semantics/exceptions, not textured-art ROI numbers. [WCAG 2.2](https://www.w3.org/TR/WCAG22/) is the accessibility reference, not a claim of compliance. No accessible label may reveal disappearance, moved destinations or correctness before discovery. Visual-memory limits remain explicit; a fully nonvisual mode is a separate product decision. Browser zoom and assistive technology are not disabled to enforce the recommended no-app-zoom observation policy.

Reduced motion removes smooth camera travel, pulsing target effects and animated transitions; use immediate scale changes and the same timed neutral blank. It does not remove the 2-second separation or extend observation. Prefer no clue-related animation in any mode.

## 8. Performance, failures and interruptions

Preload only the current case's accepted pair and required resources before timing; do not preload the case library. Use one retained Phaser runtime; no runtime recreation on camera movement, projection updates or ordinary layout resize. Clean listeners, pointer capture, observers, timers and camera callbacks on unmount. DPR affects raster cost; do not force a high backing resolution without measurement. A 960×540 RGBA buffer is ~1.98MiB, two are ~3.96MiB before texture/GPU/copies/decoding overhead; this is a size estimate, not measured memory usage. At 2× DPR raster area can quadruple if logical buffers are multiplied accordingly. Texture filtering can smooth but cannot invent source detail.

Measure load/decode readiness, frame time during gestures, dropped frames, memory and orientation reflow on actual devices. Proposed runtime goal is responsive 60Hz interaction where hardware permits, with no input misrouting or skipped/extended exposure even at lower frame rates; numeric release budgets and fallback DPR are O11.

Asset/schema/geometry mismatch before Start: remain untimed with neutral recoverable error; no partially loaded original. Active renderer failure/backgrounding/page restore: mask original first and reconcile the original absolute deadline; never refresh it. The recommended interruption policy and uncertainty handling are in [OBSERVATION_FAIRNESS.md](OBSERVATION_FAIRNESS.md) and require O09. Do not claim the current milestone-only session or bridge provides deadline persistence/rollback. Recovery must use existing architecture under a separately authorized extension. No timer/error behavior, PWA support or gesture feature is implemented by this document.
